## Gate 2b — critique the plan

Read the spec at `{{SPEC_PATH}}` and the implementation plan at `{{PLAN_PATH}}`.

The spec is settled — it passed its own gate. You are attacking the **plan**: whether this
approach, in this order, actually delivers that spec without breaking what already works.

Answer these, and only these:

1. **Coverage.** Which acceptance criterion in the spec has no step or task in the plan that
   satisfies it? Which planned step or task serves no criterion?
2. **Order and reversibility.** Which step leaves the system broken if the work stops right
   after it? Which step is hard to undo once shipped, and is it sequenced late enough to be
   worth that?
3. **Blast radius.** What existing behaviour does this touch that the plan does not mention?
   Name the concrete caller, table, endpoint or screen.
4. **Assumed decisions.** Which fork — data model, library, boundary, migration strategy — did
   the plan pick silently instead of surfacing as a decision? State the alternative it skipped.
5. **Tests.** Which planned test would pass even if the corresponding behaviour were absent or
   wrong? Which named behaviour in the plan has no test traced to it?

Judge the plan against *this* project's scale and team, per the calibration above. A plan that
is right for this project and would be wrong at ten times the scale is right.

Do not rewrite the plan. Do not estimate effort in hours. Do not review writing quality.
