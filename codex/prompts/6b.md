## Gate 6b — does the diff deliver the spec?

Review the working-tree diff against the spec at `{{SPEC_PATH}}`.
{{TASKS_SCOPE}}

Another review is running on the correctness-and-quality axis. Yours is **conformance**: what
is *missing* relative to the spec, not what is wrong with the code that exists. Staying off
the other axis is what makes running both worth the tokens.

Answer these, and only these:

1. Which acceptance criterion in the spec is **not fully satisfied** by this diff? Quote the
   criterion, then name what is absent.
2. Which behaviour introduced by this diff has **no test**? Name the behaviour, not the file.
3. Which **failure or permission case** does the diff leave unhandled — an error path, an
   empty state, an unauthorized caller, a partial write?
4. Where has the implementation **drifted** from the spec in a way the spec does not record?
   Drift is not automatically wrong, but an unrecorded decision is a finding.

For frontend changes, add: accessibility and state handling (loading, empty, error,
zero-results) measured against the criteria, not against general best practice.

Do not hunt for style, lint or formatting issues. Do not restructure the code. Do not report
what the other review is for: bugs in lines that exist.
