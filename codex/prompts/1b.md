## Gate 1b — critique the spec

Read the spec at `{{SPEC_PATH}}`.

You are attacking the **problem statement**, not a proposed solution. No code exists yet and
no implementation approach has been chosen; a finding that presumes one is out of scope.

Answer these, and only these:

1. **Acceptance criteria vs. reality.** Which stated criterion is untestable as written, or
   passes trivially without the feature working? Which edge case that this project will
   actually hit has no criterion covering it?
2. **Scope.** What is listed as in-scope but has no criterion? What is listed as out-of-scope
   in a way that leaves the in-scope part incoherent or unshippable on its own?
3. **Assumed decisions.** Which decision was made silently in the prose — a data model, a
   boundary, a default, a failure behaviour — without appearing under the spec's open
   decisions? Name the decision and where it is assumed.
4. **Operability.** Which criterion is verified only at the layer that *produces* a result,
   never at the layer that *consumes* it? Those can pass while the feature is useless to the
   person operating it.

Do not propose an implementation. Do not estimate effort. Do not review writing quality.
